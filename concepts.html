Reader, module and controller

TermMeaning
ReaderThe NDN5030 device. It has four antenna ports, Ethernet and USB-C.
RFID moduleThe RF component inside the reader. The reader firmware sends it commands and receives its tag reports. Its settings are reached through module.call.
ControllerThe program holding the reader connection, for example TCPHost, an SDK client or the Gateway. Each reader admits one controller across Ethernet and USB.
WSSSecure WebSocket over Ethernet. The factory port is 8443.
USB COMThe USB serial port of the reader used for control. Windows shows it as a COM port. It carries the same API as WSS and is available with the standard firmware image.
Reader identity over EthernetOn first use the SDK stores the reader certificate SHA-256 against board_id. It checks that association on subsequent connections, including after an IP change.
board_idThe identity of the reader. It ends with the 12 hexadecimal digits of the Ethernet MAC address. Check it after every connection.
boot_idThe identity of one boot. It changes at every restart or power cycle. A new value means that the reader no longer remembers earlier requests.

Control and reader state

TermMeaning
LeaseThe controller acquires ownership with lease.acquire and returns it with lease.release. The SDK and Gateway call lease.renew about once per second. After 5000 ms without renewal, the reader releases the lease and requests Stop for an active inventory.
Reader stateAt idle RF is off. Commands that change settings or start inventory also need a valid lease and no conflicting maintenance operation. initializing follows power-on. At unknown the RF state is unconfirmed; record the fault before power-cycling.
Operation UUIDA UUID that the application creates for one action, sent as op_id. If a reply is lost, send the same UUID with the same arguments again: the reader returns the result of the first request and does not run the action twice. The reader remembers a UUID for at least 60 seconds and forgets all of them when it restarts, so check boot_id before a late retry. The Gateway uses the Idempotency-Key header in the same way.
Volatile and saved settingsA volatile setting lasts until the reader is powered off. A setter called with persist=true asks the RFID module to keep the value.

Sessions and tag data

TermMeaning
Inventory sessionOne inventory run. inventory.start starts the session. At max_duration_ms the reader initiates Stop. The terminal session state is finished or unknown.
ObservationOne report of one tag on one antenna, with its EPC, its TID or both. A tag that stays on the antenna is reported many times. The reader sends each observation once and does not store it.
seq, last_seqEach report in a session carries a sequence number that starts at 1. last_seq is the number of the last report the reader sent.
reported_drops, input_errorsReports the reader could not queue for delivery, and errors on the data it received from the RFID module. Both are 0 in a session without errors.
outcomeHow a session ended: success, partial, failure or unknown.
Data completeThe outcome is success, every number from 1 to last_seq was received, and both counters are 0. The SDK reports this as DataComplete.

Gateway terms

TermMeaning
ScanThe Gateway record of one inventory session, identified by scan_id.
JournalThe Gateway database of scans and observations. It lets a client read data again after a lost connection.
CursorA position in the journal. Pass next_cursor in after to read the next page. An SSE event id is also a cursor.
stream_qualitypending while data is still arriving. complete when everything the reader reported is stored. partial or unknown when reports were lost or the result cannot be confirmed.
Integration tokenThe backend supplies this bearer token to the Gateway HTTPS API. The Gateway authorizes access to the reader IDs assigned to that integration.
